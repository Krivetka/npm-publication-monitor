# Appendix A. Backlog

The table lists every epic and user story of Section 2.5 with its acceptance criteria and MoSCoW priority. Acceptance criteria are written in Given/When/Then form for Must and Should stories; Could stories carry a one-line criterion.

| ID | Statement | Acceptance criteria | MoSCoW |
|---|---|---|---|
| **E1** | **Durable collection** of the registry change feed | — | Must |
| US1.1 | As an operator I want the collector to resume from its saved cursor after a restart, so that no publication is lost or counted twice. | Given a running collector with cursor N, when the process is killed and started again, then it continues from N; the journal holds every event once and the event count equals the feed's count for the period. | Must |
| US1.2 | As a researcher I want every event stored with the interval in which it appeared, so that catch-up after downtime does not look like a burst. | Given the collector was down for 30 minutes, when it catches up, then every event of the gap carries an interval of 30 minutes and stage 1 excludes it from the temporal lane. | Must |
| US1.3 | As an operator I want the journal partitioned by month, so that months of events stay queryable and prunable. | Given a new month begins, when the collector runs, then the partition for the next month exists before its first event; events of a month can be detached as one partition. | Should |
| **E2** | **Cheap filtering** without network requests (stage 1) | — | Must |
| US2.1 | As an analyst I want a burst of publications of a quiet package flagged within a minute, so that I see a hijacked package before the advisory. | Given a package with no publication in the last 24 hours, when three or more changes of it (by revision increment) arrive within 10 minutes with reliable timestamps, then the third event is a candidate with the feature `rate_package` and its value, within 60 seconds. | Must |
| US2.2 | As an analyst I want names that look like popular packages flagged on first publication, so that typosquats are visible without reading code. | Given a new package whose name is within one edit, a transposition, a homoglyph or a scope typo of a top-10 000 name, when its first event arrives, then stage 1 adds the nominal feature naming the target package. | Must |
| US2.3 | As an analyst I want every publication of a top-1 000 package checked by stage 2, so that the most consequential packages are never skipped. | Given a package in the top-1 000 by downloads, when any event of it arrives, then it is a candidate regardless of its score, with the feature `watchlist`. | Must |
| US2.4 | As a researcher I want stage 1 deterministic and free of network I/O, so that a replay of the journal reproduces production. | Given the journal and the parameter set, when the replay tool scores the journal, then the feature sets equal the stored production results for the same parameters. | Must |
| US2.5 | As an analyst I want a wave of mature packages waking up across unrelated namespaces flagged, so that worm propagation is visible. | Given the count of distinct namespaces with a mature package's first publication in 24 hours exceeds its baseline by four standard deviations within 10 minutes, when such an event arrives, then it carries the feature `breadth_mature`. | Should |
| **E3** | **Enrichment and evidence** (stage 2) | — | Must |
| US3.1 | As an analyst I want the publisher of a version compared with the release history, so that a new or returning account is a named feature. | Given a package with at least three earlier versions, when a version is published by an account that published none of them, then the result carries `publisher_new`; a return after a year by a former publisher carries `publisher_returned`. | Must |
| US3.2 | As an analyst I want scripts, size, file count, dependencies and repository compared with the version before the burst, so that manifest changes of a wave are visible on every event of it. | Given a burst of versions within 10 minutes, when any event of the burst is enriched, then the comparison baseline is the last version published before the burst, and an added install script yields `install_script_added` with its command. | Must |
| US3.3 | As an operator I want an hourly budget per external source with skipped requests recorded, so that quotas are never exceeded. | Given a source's hourly budget is exhausted, when a candidate needs that source, then the request is not sent, the event records "skipped: quota" for that source, and the hourly table counts the skip. | Must |
| US3.4 | As an analyst I want a snapshot of the package document stored at enrichment, so that evidence survives the registry's purge. | Given a candidate whose package document is fetched, when stage 2 stores its result, then the snapshot holds the versions, their times and the manifests attributed to the event, and the card serves it after the registry removes the versions. | Must |
| US3.5 | As an analyst I want the publisher's e-mail domain age checked through RDAP, so that a fresh domain is a feature while the address is never exposed. | Given a publisher with a custom e-mail domain, when the candidate is enriched, then RDAP is queried for the domain only, the answer is cached for 30 days, and a registration younger than 180 days yields `email_domain_young`. | Should |
| **E4** | **Explainable alerts and verdicts** | — | Must |
| US4.1 | As an analyst I want every alert decomposed into features with value, threshold and weight, so that I can check the verdict by hand. | Given an alert, when its card is opened, then every fired feature is listed with its lane, measured value, threshold and weight, and the weights sum to the final score. | Must |
| US4.2 | As an analyst I want an alert only when the final score reaches the threshold with stage-2 evidence, so that a stage-1 burst alone does not page me. | Given a candidate, when its final score is at least 4 and its stage-2 features weigh at least 2 (features that only confirm a removal do not count) and the package still exists in the registry, then it is an alert; otherwise it is not. | Must |
| US4.3 | As an analyst I want to record a verdict with a note, so that verdicts become the ground truth for evaluation. | Given an analyst with the token, when they submit confirmed, false positive or undecided for an event, then the verdict with time and note is stored, shown on the card and lists and returned by the findings endpoint; without the token the request is refused with 401. | Must |
| US4.4 | As an analyst I want repeated alerts for one package within six hours marked as repeats, so that a republishing pipeline does not flood the list. | Given an alert for a package, when another event of the same package reaches the threshold within six hours, then it is stored with a reference to the first alert and not counted as a new alert. | Should |
| **E5** | **Dashboard and API** | — | Must |
| US5.1 | As an operator I want the health and lag of every process on one page, so that I see within a minute when something stops. | Given the dashboard overview, when the collector has not polled for five minutes or stage 1 is more than 5 000 events behind, then the page shows the process as not running and the health endpoint returns 503. | Must |
| US5.2 | As an analyst I want a live feed that stays smooth with tens of thousands of rows, so that I can watch the registry for hours. | Given the live feed open for an hour at 1.4 events/s, when new events arrive, then only the visible rows are rendered, scrolling stays responsive, and arrivals while scrolled away are buffered behind a banner. | Must |
| US5.3 | As an analyst I want filters by package, feature, candidate and alert, so that I find what I need in seconds. | Given any list page, when a filter is chosen, then the list and its URL reflect the filter and the result returns within one second for the last 24 hours. | Must |
| US5.4 | As a researcher I want hourly statistics with charts and feature frequencies, so that I see trends and the cost of enrichment. | Given the statistics page, when a range of 24 h to 30 days is chosen, then the funnel, hourly counts, feature frequencies and source requests are shown for that range. | Should |
| US5.5 | As an integrator I want a documented REST API with an OpenAPI contract and Swagger UI, so that I can build on the data. | Given the server runs, when `/api/v1/openapi.json` is fetched, then it is a valid OpenAPI 3.1 document describing every endpoint, and Swagger UI renders it at `/api/docs`. | Must |
| US5.6 | As a maintainer I want a package page with every event, score and the maintainer-set history, so that I can answer "was this release ours?". | Given a package name, when its page is opened, then every journal event with chips, scores and verdicts is listed with the history of maintainer sets. | Should |
| US5.7 | As an analyst I want to see only the alerts on the packages I depend on, so that my daily review fits the time I have. | Given a list of package names (for example from a lock file), when the analyst opens the alert list with this list as a filter, then only alerts on these packages are shown, with their count per day for the last 14 days. | Should |
| **E6** | **Adaptive user interface** | — | Should |
| US6.1 | As an analyst I want the feed and the event card usable at phone width, so that I can review an alert from a phone. | Given a viewport of 390 px, when the feed or a card is opened, then no horizontal page scroll appears, every control is reachable and at least 44 px high, and the verdict can be recorded. | Should |
| **E7** | **Operations** | — | Should |
| US7.1 | As an operator I want an alert when the collector stops polling, so that downtime is documented, not discovered. | Given the external check polls the health endpoint every minute, when it returns 503 twice in a row, then an e-mail is sent. | Should |
| US7.2 | As an operator I want logs of all processes in one place, so that I can trace an incident across processes. | Logs of all containers are shipped to a central store and searchable by process and time. | Could |
| US7.3 | As the operator I want personal data removed on schedule and on request, so that the processing keeps the retention periods and the right to object. | Given the retention periods of Section 2.8, when the daily clean-up runs, then snapshots of candidates without an alert older than 30 days are deleted, and an account on the exclusion list is removed from stored snapshots and the maintainer-set history and is not stored again. | Should |
| **E8** | **Evaluation by replay** | — | Must |
| US8.1 | As a researcher I want incident scenarios inserted into the recorded background at random moments, so that recall and delay are measured on the real stream. | Given a scenario definition and the exported journal, when the replay runs with a seed, then the scenario is inserted at N random moments and the whole stream is scored by both stages with the same engines as production. | Must |
| US8.2 | As a researcher I want recall, precision, detection delay and request reduction reported per scenario, so that the evaluation is reproducible. | Given a replay run, when it finishes, then a report states per scenario the share of insertions with an alert, the delay from the first publication to the alert, the background alerts in the window and the source requests, and a second run with the same seed gives the same numbers. | Must |
| **E9** | **Calibration** | — | Could |
| US9.1 | As a researcher I want thresholds set from per-feature distributions on the background, so that the candidate rate stays within the stage-2 budget. | A rule set replayed on stored results reports the alerts per day it would produce; the parameter set is versioned and stored with every result. | Could |
